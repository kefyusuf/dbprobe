# dbprobe v0.1 Architecture Design

**Status:** Accepted architecture contract; implementation in progress

**Date:** 2026-08-21

## Product definition

`dbprobe` is a database intelligence runtime for deterministic, read-only diagnostics. The runtime is database-agnostic; engine knowledge lives behind adapter contracts. MySQL is the first production adapter, while MongoDB is the first planned non-relational abstraction-validation adapter before SDK stabilization.

## Core architectural rules

1. Core operates on capabilities, signals/observations, deltas and findings; it does not model a database as relational tables/rows/transactions.
2. `internal/core`, `internal/app`, `internal/platform`, `internal/surfaces` and `sdk` do not import concrete database adapters or drivers.
3. Database-specific connectivity, SQL, telemetry interpretation and engine-native findings stay under `adapters/<engine>`.
4. MVP adapter registration is compile-time in the CLI composition root. Go runtime `.so` plugins are not part of the architecture.
5. Adapter SDK is pre-1.0 until a non-relational adapter validates that relational assumptions have not leaked into the contract.
6. Diagnostics are deterministic. AI may explain/prioritize findings but does not collect evidence or decide diagnoses.
7. Inspection paths are read-only. Remediation, DDL/DML, session killing and server mutation are outside deterministic inspection.
8. Missing privileges/features reduce capabilities and report partial visibility instead of fabricating complete data.
9. Machine output is a versioned contract. The first executable report contract is `dbprobe.inspect/v1alpha1`.
10. Counter sampling/delta/reset handling belongs to the generic collection runtime, not individual database adapters.

## Adapter contract

An adapter resolves a target and opens a runtime that provides:

```go
type Runtime interface {
    Target() TargetMetadata
    Capabilities() capability.Set
    Collectors() []collector.Collector
    Rules() []finding.Rule
    SecurityProfile() SecurityProfile
    Close() error
}
```

Adapters own their native client/driver types privately. Core never sees `*sql.DB`, `*pgx.Conn`, `*mongo.Client`, `*gocql.Session`, or equivalent engine clients.

## Capability model

Capabilities represent semantic visibility, not only server feature presence. A capability is advertised only when the feature exists and the configured identity can read the evidence required by its collector/rule.

Examples:

```text
activity.sessions
activity.transactions
workload.query_summary
schema.indexes
schema.objects
locking.wait_graph
replication.status
storage.cache
query.explain

mysql.performance_schema
mysql.sys_schema
mysql.innodb
mysql.replication
```

Engine-specific concepts remain namespaced. Core must never contain checks such as `if engine == "mysql"`.

## Signal / exactness model

Observations carry stable signal keys, object references, units, collection time, sensitivity and exactness. Supported exactness labels include:

```text
scraped
cumulative
sampled
estimated
unavailable
reset
```

Cumulative counters are sampled centrally by core. Counter decreases are resets and must never become negative rates.

## Finding model

Findings are deterministic rule outputs. Portable findings use `core.*` only when semantics are genuinely portable; engine-native findings use an engine namespace.

Examples:

```text
core.connection_saturation
mysql.long_transaction
mysql.query_rows_examined_amplification
postgres.xid_wraparound
mongodb.oplog_window_small
cassandra.compaction_backlog
```

Stable finding/suppression identity must not be based on ephemeral transaction, thread, lock or process IDs. Ephemeral identifiers may appear only as bounded evidence.

## Privacy and security contract

- Credentials and full raw connection targets are never exposed in reports/errors.
- Application row/document data is never collected.
- Query literal text is not collected by default; normalized query shapes are allowed evidence.
- Engine error-message text that may embed application values is not collected unless a future explicit sensitivity/redaction contract permits it.
- Read-only execution is an adapter guarantee independent of whether the inspected server itself is configured read-only.
- Connection/driver options that can broaden execution behavior are not accepted merely because a native driver supports them.

## Baseline and temporal model

The runtime will store versioned snapshots locally (SQLite in the temporal phase), compute reset-aware deltas, compare baselines, identify query/schema regressions and correlate events. Persistence remains engine-agnostic: engine-specific signals are stored by namespaced key/object rather than dedicated database columns.

## Surfaces

Application reports are shared by all presentation surfaces:

```text
CLI
JSON
SARIF
JUnit
Prometheus
MCP
AI explanation
```

Surfaces consume the application report and do not inspect databases directly.

## MVP adapter sequence

1. Fake adapter — proves contracts/runtime without a real engine.
2. MySQL — first production adapter.
3. MongoDB architecture probe — validates non-relational abstraction boundaries before SDK stabilization.
4. PostgreSQL — relational adapter after cross-model validation.
5. Cassandra — distributed/wide-column architecture validation.

## MySQL execution note

MySQL 8.4 LTS is the primary production target. MySQL 8.0.46 remains a legacy compatibility target because the 8.0 series reached EOL in April 2026. MySQL adapter source work may progress independently, but it is not merge-ready until the complete branch passes the Go 1.25 acceptance suite and the pinned MySQL 8.0.46/8.4.11 Docker matrix.

## SDK stabilization gate

Do not publish Adapter Contract v1.0 until:

- fake adapter passes contract tests;
- MySQL production adapter passes its acceptance gate;
- a MongoDB spike implements the same core contracts without introducing relational types into core;
- privacy/exactness/capability contracts work for both relational and document models;
- external adapter protocol requirements are understood.
