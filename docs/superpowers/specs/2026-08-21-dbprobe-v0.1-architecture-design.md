# dbprobe v0.1 Architecture Design

**Status:** Proposed architecture contract for MVP

**Date:** 2026-08-21

## 1. Purpose

`dbprobe` is a database-intelligence runtime for deterministic diagnostics, temporal analysis, CI, machine-readable reporting, MCP, and optional AI-assisted explanation.

The product is **database-agnostic at the core**. Database engines are integrations implemented through adapters. MySQL is the first production adapter, MongoDB is the first abstraction-validation adapter, and additional engines such as PostgreSQL and Cassandra are expected later.

The core rule is:

> Core understands capabilities, observations, findings, snapshots, deltas, events, and policies. Adapters understand database engines.

The MVP must prove that this boundary is real rather than cosmetic.

---

## 2. Product Principles

### 2.1 Deterministic diagnosis first

Findings are produced by deterministic rules over collected evidence. An LLM may explain, summarize, prioritize, or contextualize existing findings, but it must not be the source of truth for diagnostics.

### 2.2 Read-only by default

Database inspection must not mutate application data, schema, configuration, or server state. Adapter-specific privilege requirements are explicit and capability discovery must report missing visibility rather than silently pretending the inspection is complete.

### 2.3 Temporal, not snapshot-only

A single inspection is useful, but the product becomes substantially more valuable when it can answer:

- What changed?
- Which query regressed?
- Which resource is trending toward saturation?
- Did a schema/configuration/server lifecycle event correlate with a regression?

Local baselines and deltas are therefore part of the architecture, not a later monitoring add-on.

### 2.4 Capability-driven, not engine-conditional core

Core code must not contain branches such as:

```go
if engine == "mysql" { ... }
```

Engine-specific behavior is implemented by adapters. Core plans work from declared capabilities and registered contracts.

### 2.5 Preserve engine-native semantics

The project must not force every database into relational abstractions such as `table`, `row`, `vacuum`, or `transaction`.

A MySQL InnoDB purge problem, PostgreSQL XID-wraparound risk, MongoDB WiredTiger cache problem, and Cassandra compaction backlog remain engine-native findings. Generic findings exist only when the semantics are genuinely portable.

### 2.6 Evidence and uncertainty are first-class

Every important value carries provenance and exactness. Reports must distinguish point-in-time gauges, cumulative counters, sampled rates, estimates, unavailable signals, and reset/invalidated windows.

## 3. Scope

### 3.1 MVP scope

The MVP consists of:

1. database-agnostic core runtime;
2. public adapter SDK contracts;
3. compile-time adapter registry;
4. fake adapter used for contract/TDD coverage;
5. MySQL 8.0/8.4 production adapter;
6. capability discovery;
7. signal collection and normalization;
8. deterministic finding engine;
9. local SQLite baseline store;
10. snapshot diff and regression detection;
11. terminal and versioned JSON output;
12. CLI commands necessary to inspect MySQL;
13. adapter contract tests;
14. Docker-based integration test matrix.

### 3.2 Architecture-validation scope

After the MySQL MVP is functional, a narrow MongoDB adapter spike must implement enough of the SDK to validate that the core does not accidentally depend on SQL/RDBMS concepts.

This spike should cover at least:

- server identity;
- collections/index metadata;
- query-shape observations;
- WiredTiger cache observations;
- replica-set/oplog observations where available.

The SDK is not considered stable until this validation has occurred.

### 3.3 Deferred from MVP

The following are intentionally deferred:

- runtime-loaded Go `.so` plugins;
- external adapter RPC protocol;
- public third-party adapter marketplace;
- hosted monitoring/control plane;
- continuous daemon mode;
- auto-remediation;
- write-capable recommendations/actions;
- Cassandra production adapter;
- PostgreSQL production adapter;
- full MongoDB production support;
- AI provider integration beyond the contracts required to keep the architecture open;
- remote baseline storage.

## 4. Architectural Approach

Three approaches were considered.

### Approach A — MySQL-first application with later interfaces

Build the product directly around MySQL and extract interfaces when a second engine arrives.

**Advantages**

- fastest first feature delivery;
- minimal up-front abstraction work.

**Rejected because**

- core models would almost certainly inherit MySQL/RDBMS semantics;
- extraction later would be expensive;
- the intended product is explicitly multi-engine.

### Approach B — Universal relational database model

Create generic `Database`, `Table`, `Index`, `Transaction`, and `Query` types and map every engine onto them.

**Advantages**

- superficially simple API;
- easy MySQL/PostgreSQL comparison.

**Rejected because**

- breaks down for MongoDB and Cassandra;
- produces misleading abstractions;
- leaks SQL semantics into the core.

### Approach C — Capability + signal runtime with engine adapters

Adapters advertise capabilities, collect namespaced observations, and register engine-specific rules. Core provides orchestration, temporal analysis, common rule execution, policies, rendering contracts, and storage.

**Selected.**

This approach has the highest initial design cost but best matches the product goal and prevents database semantics from being flattened incorrectly.

## 5. System Boundaries

The dependency direction is:

```text
Surfaces
   |
   v
Application
   |
   v
Core <---- SDK contracts
             ^
             |
          Adapters
```

More concretely:

```text
┌───────────────────────────────────────────────┐
│                  SURFACES                     │
│ CLI │ JSON │ SARIF* │ Metrics* │ MCP* │ AI* │
└──────────────────────┬────────────────────────┘
                       │
┌──────────────────────▼────────────────────────┐
│                APPLICATION                    │
│ inspect │ diff │ findings │ schema │ explain │
└──────────────────────┬────────────────────────┘
                       │
┌──────────────────────▼────────────────────────┐
│                    CORE                       │
│ capabilities │ signals │ collection planner  │
│ snapshots │ deltas │ events │ findings       │
│ policies │ suppression │ scoring             │
└──────────────────────┬────────────────────────┘
                       │
                 ADAPTER SDK
                       │
          ┌────────────┼─────────────┐
          │            │             │
        MySQL       MongoDB*     PostgreSQL*
                                      │
                                  Cassandra*

* deferred or architecture-validation scope
```

### Dependency invariants

The following rules are architectural tests, not conventions:

1. `internal/core` must not import MySQL, PostgreSQL, MongoDB, Cassandra, or any engine driver.
2. `sdk` must not import any adapter.
3. one adapter must not import another adapter.
4. surfaces must not directly depend on concrete adapter packages.
5. application use-cases invoke adapters only through SDK/runtime contracts.
6. baseline storage stores generic snapshots/observations and must not require engine-specific schema migrations for new signals.

## 7. Adapter Contract

### 7.1 Adapter

An adapter identifies whether it can handle a target and opens an engine-specific runtime.

Conceptual contract:

```go
type Adapter interface {
    Metadata() AdapterMetadata
    Match(target TargetSpec) bool
    Open(ctx context.Context, target TargetSpec, opts OpenOptions) (Runtime, error)
}
```

`AdapterMetadata` includes at minimum:

- stable adapter ID;
- display name;
- adapter version;
- supported engine families;
- SDK contract version.

### 7.2 Runtime

An opened runtime owns the engine connection/session and exposes only portable contracts to the application layer.

```go
type Runtime interface {
    Target() TargetMetadata
    Capabilities() CapabilitySet
    Collectors() []Collector
    Rules() []Rule
    SecurityProfile() SecurityProfile
    Close() error
}
```

The concrete database client remains private to the adapter.

Examples:

- MySQL adapter may hold `*sql.DB` internally;
- MongoDB adapter may hold `*mongo.Client` internally;
- Cassandra adapter may hold `*gocql.Session` internally.

Core must never receive those concrete values.

### 7.3 Compile-time registry

MVP adapters are statically registered into the binary.

Conceptually:

```go
registry.Register(mysql.New())
```

Go's native runtime `plugin` mechanism is explicitly not part of the MVP due to platform/version/deployment constraints.

The SDK must avoid design choices that would prevent a future out-of-process adapter protocol over stdio/RPC, but that protocol is not implemented in v0.1.

## 8. Capability Model

Capabilities describe what a connected target can actually expose.

They are namespaced strings rather than a giant fixed boolean struct.

Examples of portable capabilities:

```text
activity.sessions
activity.operations
workload.query_summary
schema.objects
schema.indexes
locking.wait_graph
replication.status
storage.cache
storage.io
query.explain
```

Examples of engine-native capabilities:

```text
mysql.performance_schema
mysql.sys_schema
mysql.innodb
mysql.binlog

mongodb.wiredtiger
mongodb.replica_set
mongodb.oplog

postgres.pg_stat_statements
postgres.vacuum
postgres.wal

cassandra.compaction
cassandra.repair
cassandra.sstable
```

Capability discovery happens after connection and before collection planning.

Missing privileges or unavailable engine features remove capabilities and produce explicit availability reasons. They do not make the entire inspection fail unless no useful inspection is possible.

---

## 9. Signal and Observation Model

A signal identifies the semantic measurement. An observation is one measured value for one object at one time/window.

Conceptual model:

```go
type Observation struct {
    Key         SignalKey
    Object      ObjectRef
    Value       Value
    Unit        Unit
    Exactness   Exactness
    CollectedAt time.Time
    Window      *TimeWindow
    Source      SourceRef
    Sensitivity Sensitivity
}
```

### 9.1 Signal namespaces

Portable signals use `core.*` only when the semantics are genuinely consistent:

```text
core.connections.used
core.connections.limit
core.query.calls
core.query.mean_latency
core.replication.lag_seconds
```

Engine-native signals remain namespaced:

```text
mysql.innodb.history_list_length
mysql.innodb.redo_utilization
mysql.query.rows_examined

mongodb.wiredtiger.cache_bytes_used
mongodb.oplog.window_seconds

postgres.xid.age
postgres.wal.retained_bytes

cassandra.compaction.pending_tasks
cassandra.tombstone.scanned
```

### 9.2 Exactness

The initial exactness values are:

- `scraped` — point-in-time observation;
- `cumulative` — monotonically/cumulatively reported counter within the engine's reset lifecycle;
- `sampled` — derived from a bounded sample window;
- `estimated` — optimizer/statistical estimate rather than execution measurement;
- `unavailable` — not observable, with a reason;
- `reset` — comparison invalidated because the underlying counter reset/restarted.

Renderers and rule evaluation must preserve these distinctions.

### 9.3 Collection strategies

Collectors declare one strategy:

- `snapshot`;
- `counter`;
- `sampled_window`.

Core owns scheduling and double-sampling for counter collectors. Adapters provide reads; they should not each reinvent sleep/delta scheduling.

---

## 10. Object Identity

Core must not model only tables/indexes/rows.

Objects use typed namespaced references:

```go
type ObjectRef struct {
    Kind string
    ID   string
}
```

Examples:

```text
mysql.instance:server-uuid
mysql.table:shop.orders
mysql.index:shop.orders.idx_customer

mongodb.collection:shop.orders
mongodb.index:shop.orders.customer_1

postgres.relation:public.orders

cassandra.table:commerce.orders
cassandra.node:node-id
```

Object IDs used for suppression and history must be stable enough not to accidentally match an unrelated future ephemeral object.

---

## 11. Collector Contract and Collection Planner

Collector contract:

```go
type Collector interface {
    Descriptor() CollectorDescriptor
    Collect(ctx context.Context, req CollectRequest) ([]Observation, error)
}
```

Descriptor declares:

- stable collector ID;
- required capabilities;
- produced signal keys;
- collection strategy;
- cost class if needed later.

The planner:

1. receives target capabilities;
2. removes unsupported collectors;
3. groups collectors by strategy;
4. runs independent safe collectors concurrently with bounded concurrency;
5. opens/closes the sampling window centrally;
6. computes deltas/rates for counters;
7. records failures as unavailable evidence where practical;
8. returns the observations that were successfully collected.

A single collector failure must not normally abort the entire inspection.

---

## 12. Findings and Rule Engine

### 12.1 Finding model

```go
type Finding struct {
    ID         FindingID
    Title      string
    Severity   Severity
    Category   Category
    Impact     Impact
    Confidence Confidence
    Exactness  Exactness
    Object     ObjectRef
    Evidence   []Evidence
    Summary    string
    Guidance   string
}
```

Finding IDs are namespaced:

```text
core.connection_saturation
core.query_regression

mysql.innodb_purge_lag
mysql.auto_increment_exhaustion
mysql.full_scan_heavy

mongodb.wiredtiger_cache_pressure

postgres.xid_wraparound

cassandra.compaction_backlog
```

### 12.2 Rule contract

```go
type Rule interface {
    ID() FindingID
    Requires() []Capability
    Evaluate(ctx AnalysisContext) []Finding
}
```

`AnalysisContext` gives a rule access to:

- current snapshot;
- selected previous/baseline snapshot;
- calculated deltas;
- target capabilities;
- collection metadata/window.

### 12.3 Generic versus engine-specific rules

Generic rules are allowed only when adapters can provide equivalent semantics. Examples include connection saturation and query regression.

Engine rules stay in their adapter when the diagnosis depends on database-specific mechanics.

The core finding engine runs both sets through the same prioritization, suppression, policy, and output pipeline.

## 13. MySQL MVP Adapter

The first production adapter targets:

- MySQL 8.0;
- MySQL 8.4 LTS.

MariaDB and Percona-specific behavior are not part of the first compatibility promise.

### 13.1 Data sources

Primary sources include:

- `performance_schema`;
- `sys` schema when available;
- `information_schema` where appropriate;
- global/status variables where safe and necessary.

### 13.2 Initial MySQL capabilities

The adapter should discover and expose capabilities for:

- server/version/identity;
- sessions;
- InnoDB transactions;
- normalized statement digests;
- indexes;
- table/statistics metadata;
- lock waits;
- InnoDB/buffer-pool metrics;
- replication status;
- configuration/status variables;
- query plan-only explain;
- schema fingerprinting.

### 13.3 Initial MySQL findings

Risk/availability:

- `core.connection_saturation`;
- `mysql.replication_stopped`;
- `core.replication_lag` where comparable semantics are available;
- `mysql.long_transaction`;
- `mysql.blocking_chain`;
- `mysql.lock_wait_long`;
- `mysql.auto_increment_exhaustion`.

Query performance:

- `core.query_regression`;
- `mysql.query_high_total_time`;
- `mysql.query_full_scan`;
- `mysql.high_rows_examined_ratio`;
- `mysql.no_good_index`;
- `mysql.disk_temp_tables`.

Schema/index:

- `mysql.unused_index`;
- `mysql.redundant_index`;
- `mysql.missing_primary_key`;
- `mysql.full_scan_heavy_table`.

InnoDB:

- `mysql.buffer_pool_hit_low`;
- `mysql.innodb_purge_lag`;
- `mysql.deadlock_rate_high`;
- `mysql.redo_pressure`.

Unused-index findings must carry observation-window/confidence caveats and must never be phrased as automatic permission to drop an index.

## 14. Temporal Intelligence and Baselines

Local persistence uses SQLite through a platform adapter owned outside database-engine adapters.

The storage model is generic and includes conceptually:

```text
targets
snapshots
observations
findings
events
trend_metrics
```

The store must not add a dedicated SQL column every time a new engine signal is introduced.

### 14.1 Target identity

Stable engine identity is produced by the engine adapter. Core hashes/canonicalizes it for local lookup.

Examples:

- MySQL: server UUID plus logical database/scope;
- PostgreSQL: system identifier plus database;
- MongoDB: deployment/replica-set identity plus database;
- Cassandra: cluster identity plus keyspace/scope.

### 14.2 Delta safety

Deltas are suppressed or marked invalid when the adapter/core detects a restart, statistics reset, topology identity change, or other lifecycle event that invalidates comparison.

A reset must never be presented as a real workload drop.

### 14.3 Query regression identity

Each adapter is responsible for producing a stable-enough normalized query identity:

- MySQL digest;
- MongoDB query shape;
- PostgreSQL query ID/normalized representation;
- future engines according to their native semantics.

Core compares normalized workload observations without knowing how the identity was constructed.

---

## 15. Events

Events represent meaningful changes inferred or observed between snapshots.

Examples:

```text
server.restarted
stats.reset
schema.object_added
schema.object_removed
schema.object_changed
config.changed
replication.role_changed
```

Engine-specific events remain namespaced when necessary.

Events carry a confidence and a bounded time range when the exact change time cannot be known. The runtime must not invent precise timestamps for changes inferred only from two snapshots.

---

## 16. Security and Privacy Contract

### 16.1 Read-only posture

Every adapter provides a `SecurityProfile` describing:

- whether the current session is operating with the intended read-only posture;
- required privileges;
- recommended optional privileges;
- missing privileges;
- capabilities unavailable because of those missing privileges.

The MySQL adapter must document the minimal practical grants separately from the core architecture.

### 16.2 Query execution

MVP diagnostics must not execute arbitrary user or agent statements.

Any future plan-inspection feature must use engine-appropriate plan-only behavior and must distinguish estimates from measured execution. Features equivalent to execution-bearing `EXPLAIN ANALYZE` are outside the read-only diagnostic default.

### 16.3 Sensitive data

Observations carry sensitivity classifications. Initial policy:

- credentials: never stored or emitted;
- row/document values: never intentionally collected;
- query literal values: redact/normalize by default;
- normalized query shapes/digests: allowed when safely produced by the engine;
- schema/object metadata: allowed;
- connection strings in errors/logs: redact secrets.

The baseline store must never persist raw credentials.

---

## 17. Output Contract

### 17.1 Terminal

Human-readable reports are findings-first:

1. target identity/status;
2. health/risk summary;
3. critical/warn/info findings;
4. healthy/verified areas where useful;
5. caveats/unavailable capabilities;
6. optional detailed sections.

### 17.2 JSON

JSON is a versioned API contract rather than a serialization accident.

Top-level structure conceptually includes:

```json
{
  "schema_version": "...",
  "collected_at": "...",
  "target": {},
  "capabilities": [],
  "collection": {},
  "observations": [],
  "deltas": [],
  "events": [],
  "findings": [],
  "warnings": []
}
```

Breaking JSON changes require schema-version changes and migration/compatibility consideration for stored baselines.

## 18. CLI Design

Portable commands in the MVP:

```text
dbprobe inspect
dbprobe findings
dbprobe diff
dbprobe queries
dbprobe indexes
dbprobe locks
dbprobe replication
dbprobe baselines
dbprobe config
```

Connection URLs select adapters where unambiguous:

```text
dbprobe inspect mysql://...
dbprobe inspect mongodb://...
dbprobe inspect postgres://...
```

Engine-native deep-dive commands can later be namespaced instead of forcing false portability:

```text
dbprobe mysql innodb
dbprobe mongodb wiredtiger
dbprobe postgres vacuum
dbprobe cassandra compaction
```

MVP implements only commands backed by MySQL functionality and core temporal behavior.

## 19. Error Handling

Errors are classified into at least:

- usage/configuration error;
- connection/authentication error;
- capability/privilege limitation;
- collector unavailable/error;
- baseline/storage error;
- internal invariant error.

Collector failures should degrade individual sections where possible. Connection failure, invalid target resolution, corrupted required configuration, or internal contract violations may fail the run.

All adapter-originated error text is passed through secret-redaction boundaries before user-visible output.

## 20. Testing Strategy

### 20.1 TDD

Core and SDK contracts are developed test-first. Production adapter collectors/rules should be driven by fixtures and integration tests before broad implementation.

### 20.2 Fake adapter

A fake adapter exists before the MySQL implementation and proves:

- adapter resolution;
- capability planning;
- snapshot collectors;
- counter double-sampling;
- unavailable capability behavior;
- findings execution;
- JSON serialization;
- baseline/diff behavior;
- error degradation.

### 20.3 Adapter contract suite

Adapters run a shared suite conceptually invoked as:

```go
adaptertest.Run(t, adapter)
```

The suite validates:

- metadata completeness;
- unique adapter/capability/signal/finding IDs;
- namespace rules;
- collector descriptor validity;
- declared produced signals;
- missing capability behavior;
- snapshot serialization;
- clean shutdown;
- error redaction expectations;
- security-profile presence;
- stable target identity semantics.

### 20.4 Integration matrix

Initial CI integration targets:

```text
MySQL 8.0
MySQL 8.4
```

Each version runs in containers and seeds deterministic workloads for findings that require runtime evidence.

### 20.5 Architecture tests

Automated dependency checks must fail CI if:

- core imports an engine driver;
- one adapter imports another;
- a surface imports a concrete adapter implementation outside the composition root;
- engine-specific signal/finding IDs violate namespace rules.

---

## 21. Versioning and Compatibility

Three contracts version independently where useful:

1. application release version;
2. JSON snapshot schema version;
3. adapter SDK contract version.

The adapter SDK remains pre-1.0 until at least MySQL plus the MongoDB architecture-validation adapter have exercised the model.

Cassandra should be treated as a second major abstraction stress test before declaring the adapter ecosystem fully stable.

---

## 22. Composition Root

Concrete adapter registration occurs only in the executable composition root or a dedicated registry bootstrap package.

Example conceptual flow:

```text
cmd/dbprobe
   -> construct core services
   -> register mysql adapter
   -> construct application use-cases
   -> bind CLI surfaces
```

This is the one place where the executable is allowed to know which concrete adapters were compiled into the binary.

## 24. MVP Acceptance Criteria

The MVP is considered successful when all of the following are true:

1. `dbprobe inspect mysql://...` completes against MySQL 8.0 and 8.4 with a read-only diagnostic profile.
2. Missing optional privileges produce explicit capability gaps rather than misleading clean results.
3. At least the agreed initial MySQL finding set is deterministic and covered by tests.
4. Counter-based metrics use bounded sampling/deltas rather than naïve cumulative values where rates are claimed.
5. A second inspection can persist a baseline and identify at least query regressions and lifecycle/reset-safe deltas.
6. JSON output is schema-versioned and round-trippable through the local baseline store.
7. The fake adapter passes the shared adapter contract suite.
8. Core packages have no imports of MySQL-specific drivers/packages.
9. A MongoDB validation adapter can collect representative non-relational signals without requiring relational concepts to be added to the core.
10. CI enforces architecture boundaries and tests MySQL 8.0/8.4.

---

## 25. Explicit Non-Goals and Guardrails

The MVP will not:

- modify schemas;
- create/drop indexes;
- kill sessions automatically;
- change database settings;
- execute arbitrary agent-generated SQL;
- claim a finding is certain when evidence is sampled/estimated/incomplete;
- treat unavailable telemetry as healthy telemetry;
- expose raw credentials;
- normalize every engine into relational terminology;
- freeze the public adapter SDK before cross-engine validation.

---

## 26. Architecture Decisions Locked by This Contract

The following decisions are considered locked for v0.1 unless a written ADR deliberately supersedes them:

1. **Product name:** `dbprobe`.
2. **Language:** Go.
3. **Architecture:** modular monolith with adapter boundaries.
4. **First production adapter:** MySQL.
5. **First abstraction-validation adapter:** MongoDB.
6. **Adapter loading:** compile-time registry for MVP.
7. **Core abstraction:** capabilities + observations + findings, not relational entities.
8. **Diagnostics:** deterministic rules are authoritative; AI is explanatory only.
9. **Temporal store:** local SQLite baseline implementation behind a generic store boundary.
10. **Safety posture:** read-only inspection and explicit partial-visibility reporting.
11. **Public machine contract:** versioned JSON schema.
12. **SDK stability:** no v1 promise until cross-engine validation.

These decisions define the implementation envelope for the next planning phase.
