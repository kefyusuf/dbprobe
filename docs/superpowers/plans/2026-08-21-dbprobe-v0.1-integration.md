# dbprobe v0.1 Integration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Consolidate the independently verified v0.1 feature branches into one integration branch without losing architecture boundaries or duplicating portable behavior at runtime.

**Architecture:** `integration-v0.1` is based on the verified Foundation Runtime head. The initial feature set was applied in dependency order as source checkpoints. Bounded follow-up work may use focused pull requests against the integration branch; the pre-driver SQLite CLI orchestration closure is tracked in PR #4. Overlapping files are resolved by preserving both contracts; no feature branch is force-rewritten.

**Tech Stack:** Go 1.25 target, GitHub Actions for repository verification, driver-independent `database/sql` persistence, and Docker MySQL acceptance for the final integration gate.

**Spec:** `docs/superpowers/specs/2026-08-21-dbprobe-v0.1-architecture-design.md`

## Global Constraints

- Never merge directly to `main` from this integration work.
- `internal/core`, `internal/app`, SDK and generic surfaces remain free of concrete database drivers/adapters except the CLI composition root.
- Generic `core.*` rules are authoritative over adapter rules with the same ID.
- MySQL SQL/driver code remains under `adapters/mysql`.
- Temporal history remains engine-agnostic.
- `database/sql` is allowed only under `internal/platform/sqlite` among common layers; concrete SQLite driver registration remains a composition concern.
- Driver-independent CLI orchestration must remain testable without importing a concrete SQLite driver.
- The default CLI must not advertise persistent history or `diff` until its concrete history-store factory passes the live persistence gate.
- Every overlap is resolved intentionally; never choose a source branch wholesale when it would discard already integrated behavior.
