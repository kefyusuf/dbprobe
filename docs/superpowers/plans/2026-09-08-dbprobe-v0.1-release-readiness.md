# dbprobe v0.1 release-readiness

## Purpose

Prepare the promoted v0.1 code line for an explicit `v0.1.0` release without making tag creation or release publication a side effect of ordinary development merges.

This document records the release contract and its verification evidence. It does not authorize creation of a tag or GitHub Release.

## Release contract

A release candidate must satisfy all of the following before publication:

- the release tag uses canonical `vMAJOR.MINOR.PATCH` form;
- the tag resolves to a commit contained in `main` history;
- annotated and lightweight tags are both bound to the dereferenced commit, not a tag-object SHA;
- the validated release commit is carried across build → publish and the remote tag is re-resolved immediately before publication;
- the tagged source reruns permanent `make ci` before artifacts are built;
- release builds are CGo-free and cover Linux amd64, Windows amd64, macOS amd64, and macOS arm64;
- release binaries embed the tag, exact release commit, and a UTC build timestamp derived from that commit;
- the same tested packaging script is exercised by normal CI and by the tag workflow;
- the artifact set contains four platform archives plus one SHA-256 checksum manifest;
- downloaded artifacts are checksum-verified again in the publish job before `gh release create`;
- build/verification runs with read-only repository permission; only the downstream publish job receives `contents: write`;
- GitHub Actions dependencies used by the release workflow are pinned by commit SHA;
- the publish job has explicit repository context and does not depend on a source checkout;
- the workflow never creates, moves, or pushes Git refs;
- the project is licensed under Apache License 2.0 with non-empty root `LICENSE` and `NOTICE` files;
- every release archive contains `LICENSE`, `NOTICE`, and `THIRD_PARTY_NOTICES.md`;
- the release packager resolves the non-main Go module graph, copies each module's upstream root legal material under `THIRD_PARTY_LICENSES/`, and fails closed when legal material cannot be resolved;
- third-party legal-material directories use a collision-free key derived from the module path and version together;
- the archived third-party notice contains a revision-resolved module inventory generated from the same graph used to collect those legal files.

The first legal-bundle implementation head `990e545e` exposed a second-order completeness defect in CI `35021900532`: the packager correctly discovered legal material for the resolved module graph, but a hand-maintained notice table omitted `github.com/cpuguy83/go-md2man/v2 v2.0.6`. The fix removed the stale-manual-inventory assumption and generates the archived module inventory from the exact same resolved graph used to collect legal files.

A later review found that replacing `/` with `__` when naming per-module legal directories was not injective. The acceptance contract first captured the collision risk at `2728e5f8`; `947940db` changed both production packaging and the contract to a lowercase hexadecimal encoding of `module path + NUL + version`, and CI `35049870794` passed the full permanent gate.

## Current release boundary

PR #14 merged the revision-bound release pipeline to `main` as `02b3df73702489c4aeeb89815c9cf55f546b682c`; post-merge main CI `34278962857` succeeded.

PR #16 selects Apache License 2.0 and closes the legal packaging gate. It adds root project legal files and requires official release archives to preserve project notices plus upstream legal material for the complete resolved Go module graph.

PR #16 still does **not** create `v0.1.0`, push a tag, or create a GitHub Release. After this PR is merged and post-merge `main` CI succeeds, the remaining consequential release actions are:

1. select the exact verified `main` commit to release;
2. explicitly create and push the `v0.1.0` tag at that revision;
3. verify the tag-triggered release workflow and published checksums/artifacts.

Tag creation and GitHub Release publication remain separate maintainer actions.
